The Pre-Launch Checklist for Vibe-Coded Apps

Built it with Cursor, Claude, Lovable, Bolt or v0? Most launch checklists stop at security. This one covers the whole launch: security, payments, SEO, legal pages, copy and mobile.

How to use this checklist

Work through it on your production URL, not localhost. Each item has a short why and a how to check. Anything in Security or Payments that fails is a launch blocker; the rest you can fix in your first week if you must.

1. Security: keys, data and access

  1. No secret keys in your code or git history. AI tools often paste keys inline to "just make it work", and deleting them later leaves them in history. How to check: run a free scanner such as gitleaks or trufflehog over the whole repo history. If anything real turns up, rotate the key first, then clean history.
  2. No server secrets shipped to the browser. Anything prefixed NEXT_PUBLIC_, VITE_ or REACT_APP_ is bundled into public JavaScript. How to check: open your live site, view the JS bundles in dev tools (Sources), and search for sk_, service_role, secret and your provider names.
  3. No .env or config files served publicly. A misplaced file in the public folder is readable by anyone. How to check: on your own domain, request /.env, /.env.local and /.git/config. Each should return 404, not file contents. Also confirm .env* is in .gitignore.
  4. Database rules actually restrict access. Supabase tables without Row Level Security, or Firebase rules like allow read, write: if true, let anyone with your public key read or edit everything. How to check: in Supabase, confirm RLS is enabled on every table in the exposed schema and each has policies. In Firebase, read your Firestore/Storage rules and test them in the Rules Playground as a signed-out user.
  5. Users can only see their own data (no IDOR). Endpoints like /api/orders/123 often trust the ID in the URL. How to check: sign in as user A, note a record ID, sign in as user B in another browser, and request A's record. You should get 403 or 404.
  6. Auth is enforced on the server, not just hidden in the UI. Hiding an admin button doesn't protect the admin API. How to check: call your protected API routes with no session cookie or token (curl or dev tools) and confirm they refuse.
  7. CORS is not wide open on authenticated APIs. Access-Control-Allow-Origin: * combined with credentials is a common copy-paste fix. How to check: inspect API response headers in dev tools (Network). Allowed origins should be your own domains.
  8. Rate limits on login, signup and expensive endpoints. Without them, anyone can brute-force passwords or run up your AI API bill. How to check: send a burst of requests to the endpoint (on your own app only) and confirm you start getting 429 responses.
  9. Basic security headers are set. HSTS, Content-Security-Policy, X-Content-Type-Options and a frame policy are cheap to add. How to check: run curl -I https://yourdomain and look for strict-transport-security, content-security-policy, x-content-type-options and x-frame-options or CSP frame-ancestors.

2. Payments: working end to end

  1. Every buy button goes to a real checkout. Placeholder links and href="#" are easy to miss. How to check: click every pricing and upgrade button on the live site and confirm each opens the right product at the right price.
  2. A full test purchase succeeds. How to check: use your provider's test mode and test card, complete checkout, and confirm you land on a working success page.
  3. Webhooks unlock what the customer paid for. If the webhook fails, people pay and get nothing. How to check: after the test purchase, confirm the account or order updated, and check the provider's webhook log for successful (2xx) deliveries. Verify you check the webhook signature.
  4. Receipts and confirmation emails arrive. How to check: use a real inbox for the test purchase and confirm the receipt arrives and isn't in spam.
  5. Refunds and cancellations work. How to check: refund the test order and cancel a test subscription; confirm access is removed or kept according to your own policy.
  6. Live keys in production, test keys everywhere else. Launching in test mode means nobody can actually pay. How to check: confirm production env vars use live keys and the live webhook endpoint, then make one small real purchase and refund it.

3. SEO and indexing

  1. No leftover noindex. Staging settings sometimes ship to production and keep you out of search entirely. How to check: view source and search for noindex; also check the X-Robots-Tag response header.
  2. Unique title and meta description on every page. Templates often leave "Vite App" or "Create Next App". How to check: view source on each key page and read the <title> and meta name="description".
  3. Link previews look right. Your launch post will be judged by its preview card. How to check: confirm og:title, og:description and og:image are set, then paste your URL into a private chat or post draft to preview it.
  4. robots.txt doesn't block the site. How to check: open /robots.txt and make sure there's no Disallow: / for all user agents.
  5. A sitemap exists and lists real URLs. How to check: open /sitemap.xml, confirm it uses your production domain, and submit it in Google Search Console.
  6. Canonical tags point to the right domain. A canonical pointing at a preview URL tells search engines to index the wrong site. How to check: search the source for rel="canonical" and confirm it uses your live domain.

4. Legal pages

This is a practical checklist, not legal advice.

  1. Privacy policy that matches what you actually collect. Payment providers and app stores generally expect one. How to check: list every tool that touches user data (auth, analytics, email, payments, AI APIs) and confirm the policy mentions each.
  2. Terms of service. How to check: confirm a terms page exists, is linked in the footer, and names your product and contact details.
  3. Refund policy, if you charge. Buyers look for it, and payment providers may ask for one. How to check: make sure it's linked from your pricing page and matches what your payment setup actually does.
  4. Cookie notice where it's needed. If you use non-essential cookies or tracking and have visitors in regions that require consent, you need a notice. How to check: open the site in a fresh private window, look at cookies set in dev tools (Application), and confirm your notice covers them.
  5. Legal links actually work. A footer word "Privacy" with no link doesn't count. How to check: click each footer link and confirm it loads a real page.

5. Copy: what visitors actually read

  1. No leftover TODO, DRAFT or lorem ipsum. AI-generated pages often contain notes to yourself. How to check: search your source and rendered pages for TODO, DRAFT, lorem, placeholder, example.com and [brackets].
  2. No dead calls to action. Buttons that go nowhere lose the visitors you worked hardest to get. How to check: click every button and link, including ones that only appear after JavaScript loads, and run a broken-link checker.
  3. Every claim is one you can back up. Invented user counts, fake testimonials and "trusted by" logos damage trust and can create legal risk. How to check: read each number, quote and logo and ask, "Could I prove this today?" If not, cut it.
  4. The page says what it does in one line. How to check: show the top of your page to someone for five seconds and ask what the product does.

6. Mobile and accessibility

  1. Layout works on a phone. A lot of launch-day traffic comes from social apps on mobile. How to check: use dev tools device mode at 375px wide, then test on a real phone. Look for sideways scrolling and cut-off buttons.
  2. Signup and checkout work on mobile. How to check: complete the full signup and test checkout on a phone.
  3. Images have alt text and form fields have labels. How to check: run Lighthouse's accessibility audit in Chrome dev tools and fix the flagged items.
  4. Text is readable and keyboard navigation works. How to check: Tab through the page and confirm you can reach and see focus on every control; Lighthouse also flags low contrast.
  5. The page loads fast enough. How to check: run Lighthouse in mobile mode and address the largest images and blocking scripts first.

FAQ

What is a pre-launch audit for a vibe-coded app?

A pass over your live site and code before you announce it, looking for the problems AI coding tools commonly leave behind: exposed keys, open database rules, broken checkout, missing SEO tags, absent legal pages, leftover draft text and mobile layout issues.

Is security the only thing I need to check before launch?

No. A secure app that can't take payment, is set to noindex, or still shows TODO text will still have a bad launch.

Can I run this checklist myself?

Yes. Every item includes how to check it with free tools like browser dev tools, curl and git. The Standard Audit runs the same checks for you and ranks the fixes.

What does the $49 Standard Audit include?

Do you need access to my repository?

No. A site-only audit works. Read-only repo access adds the secret-scanning and database-rule checks.
